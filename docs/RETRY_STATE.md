# 失败重试与输入状态

2026-10-22，修复独立审查 FE-014（基线3df0b55）。公开样本工作台与本地Python工作台使用同一套界面。

## 用户能观察到的变化

2023收入同比缺少2022资料，返回FACTS_NOT_FOUND。原来改选2024后点击“重试”仍执行2023；改正中文检索词后也仍重复旧查询。重试回调捕获了失败时的data，而输入变化只清空结果。

现在，公司、年度、任务或查询发生变化时，清空结果的同时注销旧重试回调并隐藏按钮。用户通过“运行核查”明确提交当前输入；不自动发起模型请求。未修改输入时仍可手动重试原请求，初始化资料失败仍可重新加载。

`web/app.mjs`的`clearResult`统一清理结果与重试权限。它也用于新请求开始，所以成功后不残留上次失败的重试回调。失败分支可以为本次请求重新建立回调。只隐藏按钮不够：旧回调必须一起清除。

## 可复跑验收

```sh
python3 -m finevidence.server
# 另一个终端；可使用已有Chrome或安装好的测试浏览器
node tests/browser-retry.cjs
# 包含原有14项流程和新增7项重试检查
pnpm test:browser
```

与原浏览器脚本相同，BASE_URL指定静态或Python工作台，BROWSER_ARTIFACTS指定截图和JSON输出，CHROME_PATH可指定已有Chrome。新脚本在结果文件中记录每项通过／失败，并在任一失败时退出1。CI的两种运行模式都执行它。

七项固定场景：年度修改、查询修改、公司修改、任务修改、参数未变的业务拒绝重试、参数未变的网络故障重试、模型辅助失败后切换固定流程。前四项走实际应用与数据；最后两个故障／模型分支只在浏览器HTTP边界使用明确标注的离线响应夹具，拦截全部模拟API请求，不调用外部模型。界面事件、fetch、状态和结果渲染仍实际执行。

新测试先在未修复的本地页和公开页各得到2/7：四种输入修改与模型切换失败，两个原参数重试对照原已成功。两行生产修复后，本地与静态页各7/7；原有14项流程、Python181项（21.045秒）、JS7项和固定合成开发任务8/8保持。故意只保留隐藏按钮、移除回调注销时，新测试6/7，模型切换项明确失败；恢复完整修复后7/7。最终CI和公开部署证据记录在发布材料中。没有放宽旧断言。

这是工程交互场景的效果：五个失败状态迁移修复，而非金融任务准确率、真实报表质量或人力收益。真实模型首轮8题仍7/8，FE-013保持开放；本轮0付费模型调用。
